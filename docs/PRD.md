# Agent Roundtable 产品需求文档

**文档状态：** Draft v0.1  
**更新日期：** 2026-10-25  
**产品形态：** iOS 原生 App + Django 后端服务  
**目标平台顺序：** iOS 先行，Android 后补  
**代码管理：** GitHub

## 1. 产品概述

### 1.1 产品定位

Agent Roundtable 是一个面向移动端的 AI 多智能体圆桌应用。用户提出一个具体问题并选择多个具有不同立场的 AI Agent，Agent 之间按照受控规则进行多轮讨论、引用和评价彼此的观点，最终输出共识、分歧和建议。

它不是普通角色聊天室，也不是无限自动对话。产品的核心价值是：

> 用多人讨论的形式获得比单次问答更丰富的视角，并把讨论收敛为可理解、可分享的结论。

### 1.2 背景与问题

现有 AI 对话产品大多是一对一问答，用户只能得到单一模型的一次回答。部分产品支持多角色群聊，但常见问题包括：

- 角色只是换了名字，观点同质化。
- AI 之间没有明确引用关系，只是在轮流说话。
- 对话容易跑题或无限继续。
- 没有共识、分歧和行动建议。
- 用户只能看，难以暂停、点名或改变讨论方向。
- 长对话成本高，且断线后难以恢复。

### 1.3 产品机会

本产品将“群聊感”和“结构化讨论”结合：

- 角色有不同目标、立场和表达方式。
- 发言由调度器决定，不由固定轮转决定。
- Agent 可以主动选择不发言。
- 评价必须引用具体观点，并标记支持、反对、补充或质疑。
- 用户是群成员，可以中断和重定向讨论。
- 每轮讨论有轮数和 Token 预算，最终自动收敛。
- 原生移动端完整呈现正在思考、正在输入、引用关系和讨论状态。

## 2. 产品目标

### 2.1 用户目标

- 在 60 秒内创建一个可开始的 AI 圆桌。
- 获得至少两个相互不同的有效观点。
- 看懂 AI 在哪里达成共识、在哪里存在分歧。
- 可以把结论保存或分享。
- 可在讨论过程中随时接管。

### 2.2 项目目标

- 展示 SwiftUI 原生开发、实时通信、状态恢复和复杂聊天界面能力。
- 展示 Django 后端、WebSocket、Agent 调度和 LLM 工程能力。
- 形成可公开演示的 GitHub 项目、APK/TestFlight 版本及技术文档。
- 为后续 Android 客户端复用同一套 API 和事件协议。

### 2.3 成功指标

MVP 上线测试后统计，不在开发前伪造数据：

- 创建圆桌后成功进入讨论的比例不低于 80%。
- 至少完成两轮讨论的会话比例不低于 60%。
- 生成有效结论的会话比例不低于 70%。
- 结论卡导出或分享率不低于 20%。
- App 崩溃会话率低于 0.5%。
- 网络恢复后 5 秒内可继续接收事件。
- 用户可读懂并复述结论中的共识和主要分歧。

## 3. 目标用户

### 3.1 核心用户

- 需要比较多个方案的个人用户。
- 希望快速获得多视角建议的学生和年轻职场人。
- 对 AI 群聊、角色互动和协作工具有兴趣的早期用户。

### 3.2 典型场景

- 旅行计划：预算、路线和体验之间的权衡。
- 消费决策：不同产品的优劣讨论。
- 学习讨论：不同解释方式之间的比较。
- 产品脑暴：多个角色从用户、技术和商业角度提出观点。
- 轻量辩论：正反双方讨论一个明确议题。

### 3.3 非目标用户

- 需要多人真人实时协作的团队。
- 需要专业法律、医疗或金融结论的用户。
- 需要无限角色陪伴或纯娱乐聊天室的用户。

## 4. 产品原则

1. **问题优先：** 圆桌始终围绕用户提出的明确议题。
2. **结构优先：** 每条观点可识别主张、立场、引用和依据。
3. **用户控制：** 用户可随时暂停、插话、点名和结束。
4. **有限自治：** Agent 可自主决定是否发言，但必须受轮数、时间和成本约束。
5. **可恢复：** 断网、切后台或进程终止后仍可恢复讨论。
6. **诚实标注：** 所有参与者均为 AI，不冒充真人或公众人物。
7. **原生体验：** iOS 端使用 SwiftUI 实现，不做 Web 套壳。

## 6. 用户流程

### 6.1 首次进入

1. 用户打开 App。
2. 首页展示产品说明、最近圆桌和“新建圆桌”。
3. 用户无需登录即可开始体验。
4. 首次使用时自动创建匿名会话标识。

### 6.2 创建圆桌

1. 用户输入议题。
2. 用户从预设 Agent 中选择 3 个参与者。
3. 系统展示每个 Agent 的定位和发言风格。
4. 用户选择讨论模式；MVP 仅开放“决策讨论”。
5. 用户确认轮数和成本预算；默认两轮。
6. 用户点击“开始讨论”。

### 6.3 观看讨论

1. 主持人生成简短议程。
2. 每个 Agent 依次表达第一轮观点。
3. 界面显示“正在思考”“正在输入”或“选择沉默”。
4. 第二轮由调度器选择发言者。
5. 每个发言可引用其他 Agent 的具体观点。
6. 用户可随时插入消息或暂停讨论。

### 6.4 用户介入

用户可执行以下操作：

- 直接发送一条群聊消息。
- 点名某个 Agent 回答。
- 要求某个 Agent 只评价、不提出新方案。
- 暂停或继续自动讨论。
- 提前结束并生成结论。
- 将某条消息标记为关键观点。

### 6.5 生成结论

讨论结束后，主持人从以下维度生成结论：

- 已达成共识。
- 主要分歧。
- 各观点的理由和依据。
- 推荐方案或下一步行动。
- 仍需用户确认的问题。

### 6.6 保存与分享

1. 用户可保存结论到本地历史。
2. 用户可生成一张结论卡。
3. 结论卡支持系统分享。
4. 分享内容只包含公开讨论内容，不包含匿名标识或私有记忆。

## 7. 功能需求

### 7.1 匿名会话与账号

- MVP 使用匿名设备会话。
- 匿名会话标识由后端生成，并以安全方式保存在设备端。
- 用户无需注册即可创建和恢复自己的圆桌。
- P1 支持 Apple 登录和跨设备同步。

### 7.2 首页与历史

- 展示最近圆桌。
- 展示进行中、已完成和已归档状态。
- 支持删除本地历史。
- 无网络时可查看已缓存的圆桌和结论。

### 7.3 创建与编辑圆桌

- 议题必填，长度建议 10-500 字。
- 选择 3 个 Agent 后开始；P1 支持 2-4 个。
- 展示 Agent 的角色、目标、立场和语气。
- 默认讨论两轮，最多三轮。
- 可配置单次讨论的 Token 预算档位，不暴露复杂参数。

### 7.4 Agent 角色

MVP 提供以下预设角色：

- **方案派：** 主动提出方案和行动步骤。
- **质疑派：** 识别风险、漏洞和反例。
- **体验派：** 从用户感受和可执行性评价方案。
- **主持人：** 不可被用户直接选择，负责议程、调度和总结。

每个 Agent 必须包含：

- 身份和专长。
- 当前目标。
- 默认立场。
- 表达风格。
- 禁止行为。
- 最大发言长度。

### 7.5 发言调度

调度器根据以下因素决定下一位发言者：

- 是否被用户或 Agent 点名。
- 是否被要求回应。
- 与当前议题的相关度。
- 是否持有不同立场。
- 距离上次发言的时间。
- 是否与已有观点重复。
- 当前轮数和剩余 Token 预算。

低优先级 Agent 可以明确选择“沉默”，界面应展示该状态。

### 7.6 讨论轮次

- **第 0 步：** 主持人生成讨论议程。
- **第一轮：** Agent 独立表达观点，不重复已有主张。
- **第二轮：** 每位参与者至少引用并评价一条其他观点。
- **可选第三轮：** 仅用于回应用户插话或解决关键分歧。
- 达到最大轮数、预算耗尽或主持人判断已收敛时结束。

### 7.7 结构化发言

每条 Agent 发言至少包含：

- 发言者。
- 消息类型。
- 一句话主张。
- 正文。
- 引用消息 ID。
- 对其他观点的立场。
- 可选的挑战对象。
- 置信度。

消息类型包括：

- `proposal`：提出方案。
- `support`：支持观点。
- `challenge`：质疑观点。
- `supplement`：补充观点。
- `question`：提出问题。
- `pass`：选择沉默。
- `summary`：阶段或最终总结。

### 7.8 用户控制

- 用户可以发送普通消息。
- 用户可以 `@` 某个 Agent。
- 用户可以暂停自动讨论。
- 用户可以要求重新生成当前 Agent 的回复。
- 用户可以提前结束。
- 用户不能删除其他参与者的已完成消息，只能隐藏本地显示。

### 7.9 总结

- 总结必须引用讨论中的具体观点。
- 总结区分共识、分歧、建议和未决问题。
- 总结不允许引入讨论中没有出现的新事实。
- 模型失败时可回退到规则化摘要，并标明“降级总结”。

### 7.10 结论卡

- 卡片包含议题、三个 Agent、主要观点、共识、分歧和建议。
- 由原生 SwiftUI 绘制。
- 支持保存到相册和系统分享。
- 卡片不包含 API Key、内部 ID 或未公开的 Prompt。

### 7.11 实时状态

界面需要展示：

- 当前轮次。
- 当前正在思考或发言的 Agent。
- 其他 Agent 的等待或沉默状态。
- 网络连接状态。
- 剩余预算的简化表示。
- 用户可以暂停和结束。

### 7.12 错误与恢复

- 网络断开时保留已有消息并显示离线提示。
- 网络恢复后从最后事件游标继续。
- 重复事件必须去重。
- 单个 Agent 失败不影响其他 Agent 已完成的内容。
- 整个房间失败时保留草稿并允许重试。
- App 被终止后，重新打开可恢复最近房间的界面状态。

## 13. 领域模型

## 14. API 与事件协议

### 14.1 REST

- 创建匿名会话。
- 获取预设 Agent。
- 创建圆桌。
- 获取圆桌详情和历史。
- 暂停、继续和结束圆桌。
- 获取最终总结。
- 删除圆桌。

### 14.2 WebSocket 事件

- `room.joined`
- `round.started`
- `agent.thinking`
- `agent.typing`
- `agent.passed`
- `message.delta`
- `message.completed`
- `round.completed`
- `summary.started`
- `summary.delta`
- `summary.completed`
- `room.failed`

所有事件必须包含：

- `event_id`
- `room_id`
- `sequence`
- `created_at`
- `event_type`
- `payload`

### 14.3 恢复协议

- 客户端保存最后处理的 `sequence`。
- 重连时携带最后游标。
- 服务端补发游标之后的事件。
- 客户端按事件 ID 去重。
- 服务端保留有限时间窗口的事件历史。

## 15. Agent 调度与安全

### 15.1 调度约束

- 最多 4 个 Agent，MVP 固定 3 个。
- 最多 3 轮。
- 单条 Agent 发言最长 1,200 字；可配置。
- 单次圆桌有 Token 预算上限。
- 同一 Agent 连续发言需满足点名、直接回复或用户要求。
- 低相关度 Agent 必须可以 `pass`。
- 主持人不得代替 Agent 发表其未生成的观点。

### 15.2 结构化输出

Agent 输出必须经过后端校验：

- 消息类型合法。
- 引用消息属于当前圆桌。
- 立场值合法。
- 挑战对象在当前参与者中。
- 正文长度符合限制。
- 不得包含内部系统 Prompt。

非法输出应重试一次；再次失败则转换为失败状态，不影响已完成的讨论。

### 15.3 内容安全

- 明确标识所有 Agent 为 AI。
- 阻止冒充真实公众人物。
- 对违法、危险、仇恨和不适宜内容进行基础过滤。
- 安全和隐私说明必须在设置页可见。
- 用户可以删除自己的圆桌和匿名会话数据。

## 16. 非功能需求

### 16.1 性能

- 目标设备冷启动时间低于 2 秒。
- 消息列表滚动保持流畅。
- 流式消息只更新变化部分。
- 进入已有圆桌时首屏内容在 1 秒内出现。
- 正常网络下首个流式事件目标在 3 秒内到达。

### 16.2 可靠性

- 所有事件至少一次投递，客户端负责去重。
- 连接恢复后不丢失已完成消息。
- 单个 Agent 失败不阻塞整个圆桌。
- 服务端异常时保留用户输入。

### 16.3 安全

- 全部生产请求使用 HTTPS/WSS。
- LLM API Key 仅保存在服务端。
- 用户输入与模型输出进行长度和格式校验。
- 日志不得记录完整敏感 Prompt，除非显式开启调试模式。
- 匿名 Token 可轮换和失效。

### 16.4 可观测性

每个圆桌记录：

- 创建、开始和结束时间。
- 各轮次耗时。
- 每个 Agent 的模型、Token 和延迟。
- 重试次数和失败原因。
- 总结是否降级。
- 事件补发次数。

### 16.5 可访问性

- VoiceOver 可识别消息发送者、状态和引用关系。
- 深色模式完整适配。
- 使用系统字体和控制尺寸。
- 颜色不是区分立场的唯一手段。

## 17. 测试策略

### 17.1 外部行为优先

测试验证用户可观察行为，不绑定内部实现：

- 创建圆桌后返回可识别的房间标识。
- 三个 Agent 各自最多发言规定次数。
- 每条评价引用有效消息。
- 达到最大轮数时停止。

- 断线重连后没有重复消息。
- 总结包含共识和分歧字段。
- App 冷启动后能恢复最近房间。

### 17.2 后端

- 调度器单元测试。

### 17.3 iOS

- WebSocket 重连与游标恢复测试。
- SwiftData 持久化测试。
- 关键流程 UI 测试。
- 真机或模拟器性能检查。

### 17.4 手工验收

至少准备三个演示议题：

1. 旅行决策。
2. 产品方案比较。

每个议题都必须验证：

- 创建流程。

## 20. 风险与开放问题

### 20.1 主要风险

- 多 Agent 成本高于单次问答。
- Agent 输出可能重复、空泛或互相附和。
- WebSocket 重连和事件去重容易出错。
- SwiftUI 长消息流可能出现性能问题。
- 模型输出格式不稳定。
- iOS 真机与 TestFlight 需要 Apple Developer 配置。
- 多 Agent 产品已有竞品，必须在结构和结论质量上形成差异。

### 20.2 待决策

1. GitHub 仓库名称、所有者和公开/私有策略。
2. 首个正式 LLM Provider 与模型。
3. 后端演示环境部署位置。
4. 是否在 MVP 加入 TestFlight 分发。
5. 内容审核使用模型审核、规则审核还是组合方案。
6. 匿名会话的过期周期。
7. 是否在 MVP 支持自定义 Agent。
8. 结论卡是否包含二维码或公开分享链接。

### 20.3 推荐默认值

- 仓库：私有开发，MVP 后公开。
- 模型：OpenAI-compatible Provider，MVP 使用 Mock 作为默认演示。
- Agent：固定三个预设角色。
- 会话：匿名模式，保留 90 天。
- 安全：规则过滤 + 模型审核。
- 分享：MVP 只分享本地生成的结论图片。
