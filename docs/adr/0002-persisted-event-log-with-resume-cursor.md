# 实时事件使用持久化事件日志，客户端按游标补发

**Status:** accepted

圆桌的实时状态（轮次开始、Agent 状态、发言完成）以事件形式写入 PostgreSQL 的 `room_event` 表，每个圆桌内 `sequence` 单调递增 1，`event_id` 全局唯一。WebSocket 连接建立时，客户端携带最后处理的 `sequence`，服务端先发送 `room.joined` 快照，再按序补发 `sequence > cursor` 的历史事件。

`room.joined` 是连接时生成的快照，不写入日志，`sequence` 固定为 0，因此不会污染游标。

服务端只补发 `ROOM_EVENT_REPLAY_WINDOW_DAYS`（默认 90 天）内的事件，并在 `room.joined.payload.replay` 返回窗口边界。若请求游标与窗口之间存在缺口，`cursor_expired = true`，客户端必须用完整的 `room.joined` 快照重置投影和游标，而不是继续部分补发。

## Considered Options

- **只广播、不落盘**：实现最简单，但断线后无法补发，也无法在重连时保证“已完成的消息不丢”（PRD 16.2）。
- **客户端每次重连拉全量消息**：可行，但消息与状态事件是两类数据，状态（思考/沉默/轮次）会被遗漏；且长讨论下全量拉取成本高。
- **持久化事件日志 + 游标补发**：多一张表、多一次写入，但断线恢复、去重和多端一致性共用同一条路径，并且为 Android 复用协议打底。

## Consequences

- 每个事件一次数据库写入；切片中事件量很小，后续若成为瓶颈可在调度器侧批量写入。
- 事件表的持久清理与匿名数据保留策略由隐私切片处理；当前补发查询已经严格执行 90 天窗口，窗口外事件不会造成部分 replay。
- 客户端必须实现按 `event_id` 去重与按 `sequence` 推进游标；`room.joined` 的 0 序号是协议的一部分，不能“顺手”改成当前最大序号。
- 本地缓存游标优先于服务端快照的 `last_sequence`；新增连接不能覆盖最后已处理游标。
- Mock 切片中的 `mock.run` 命令只是临时驱动，事件日志本身与真实调度器无关，Issue #5 可直接替换驱动方而不改协议。
