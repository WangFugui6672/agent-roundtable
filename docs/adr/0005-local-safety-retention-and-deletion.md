# 内容安全在本机执行，数据按圆桌最后活动保留 90 天

**Status:** accepted

## 背景

BYOK 架构下，用户输入和模型输出由 iOS 直连 Provider，Django 不接触 API Key，也不代理模型请求。MVP 又明确不引入服务端模型审核。因此内容过滤必须在发送前和展示前由客户端执行，同时服务端仍需提供可审计的举报、保留和删除能力。

## 决策

1. `RoundtableCore.ContentPolicy` 在本机返回 `allow | block | flag`。`block` 不发送内容；`flag` 继续但明确提示未经审核。
2. 举报只是用户提交，固定状态为 `submitted`，不自动改写消息或生成审核结论。
3. 隐藏与内容标记属于本地 SwiftData 状态，不写回服务端消息。
4. 圆桌及全部关联内容使用 `last_activity_at` 作为唯一 90 天保留锚点。创建、打开房间、消息、turn、控制、举报和结论更新都续期。
5. 删除圆桌通过幂等 REST API 立即级联清理服务端数据；客户端在服务端成功后清理本机缓存。API Key 不参与任何保留或圆桌删除。
6. 匿名会话标识放入独立 Keychain service；第三方提示确认状态可以放 UserDefaults，但不得混入秘密。

## Considered Options

- **服务端托管模型审核：** 能统一策略和审计，但需要代理模型请求，破坏 BYOK 与密钥边界。
- **只按单一关键词过滤：** 实现快，但误报高，也无法表达“标记但不阻断”。
- **不提供举报/隐藏：** 实现最少，但用户无法处理误报或表达安全关切。
- **以 GuestSession 最后访问时间清理：** 简单，但会让最近打开过的旧圆桌继续保留，或误删仍有活动的数据。
- **API Key 随房间删除：** 看似彻底，但会让删除单个圆桌意外破坏用户其他圆桌的 Provider 配置。

## Consequences

- 本地规则是有限的第一道过滤，不能保证覆盖所有语义变体；规则边界和误报策略记录在 `docs/content-safety.md`。
- `flag` 和 `reported` 不是违规判定，UI 必须避免使用“已审核”“安全”等措辞。
- 清理任务需要由部署环境定时调用 `purge_roundtables`；MVP 先在仓库提供命令，Release 阶段接入运行环境调度。
- 90 天清理以圆桌为单位删除关联数据，避免留下孤立消息、事件、结论、用量或举报。
