# 检索增强在客户端完成，不走服务端

**Status:** accepted

资料库的分块、向量化与检索全部在客户端本地执行，Django 不参与、也不知道资料库的存在。当前仅 Android 客户端实现；iOS 尚未接入。Agent 的 prompt 本来就在客户端由 `AgentPrompt` 组装后直连 Provider，RAG 只是在这条既有路径上增加一段检索到的参考资料，不需要新增接口、事件或数据库表。

嵌入模型选 `bge-small-zh-v1.5`（24M 参数、512 维、4 层、MIT 许可）的 int8 量化版，模型文件合计 22.9 MB，随 APK / App Bundle 一起分发。

## Considered Options

- **服务端 RAG**：可利用更大的嵌入模型和共享知识库，但违背 BYOK 信任边界——用户导入的文档会被上传到我们自己的服务器，而当前架构刻意保证用户内容在客户端处理。同时需要新增上传、解析、检索、权限四套接口，4 周内做不完。
- **`bge-large-zh-v1.5`（1024 维 / 24 层 / 90 MB）**：中文语义效果更好，但推理成本约为 small 的 6 倍，且 90 MB 无法打进安装包，需要额外的模型下载器和 SHA256 校验。
- **MNN 的 `bge-large-zh-MNN`（207 MB）**：能同时展示 MNN 端侧推理，但模型发布于 2024-09 后停更，且 MNN 在 Android 上没有可用的 Java 绑定，需要自写 NDK + JNI 层。
- **随包分发 small 模型**：安装包增大 22.9 MB，换来零下载、零校验、零失败路径，离线可用。

## Consequences

- 当前只有 Android 有一份 RAG 实现，iOS 未接入。若将来 iOS 接入，必须复用 `GLOSSARY.md` 中资料库、文档块、检索结果、相似度阈值的同一套语义，否则两端对同一份文档会给出不同的讨论结果。
- 因为 iOS 未接入，RAG 不能作为产品级能力对外宣传，只能作为 Android 客户端章节下的能力描述。
- 资料库只在单台设备上存在，换机即丢失；这是刻意接受的代价，不是缺陷。
- 相似度阈值按 `bge-small-zh-v1.5` 的分数分布标定（实测 0.45：相关查询 10/10 通过，无关查询 0/6 误命中）。更换模型必须重新标定阈值。
- 模型文件随安装包分发，升级模型等于发版，不能热更新。
